# UI Polish Skill

## 目标
统一并持续优化后台前端的 UI / UX 质量，重点关注：

- 弹窗
- 表单
- 列表工具栏
- 表格
- 颜色
- 字体
- 间距
- 视觉层级
- 响应式
- 可访问性

本 skill 的目标不是“做炫”，而是：

- 更清晰
- 更统一
- 更简洁
- 更稳定
- 更适合高频后台操作

---

## 一、总原则

### 1. 优先级
所有 UI 改动，按以下优先级判断：

1. 布局是否正确
2. 响应式是否会崩
3. 信息层级是否清晰
4. 交互是否顺手
5. 是否优先复用 shared wrappers
6. 是否优先复用 shadcn/ui
7. 颜色、字体、间距是否符合规范
8. a11y 是否达标

### 2. 基本要求
- 优先复用 shadcn/ui + shared wrappers
- 不新增平行基础 UI 层
- 不为单页临时造一套样式体系
- 能用统一壳解决的问题，不要页面手写
- 高级项默认折叠，低频项默认收起
- 主任务优先，装饰性视觉降级

### 3. 明确禁止
- 卡片套卡片
- 页面和弹窗里堆很多无意义容器
- 窄宽度下硬撑桌面布局
- 中文标签逐字竖排
- 用颜色装饰代替语义表达
- 大量直写颜色类打散 token 体系
- shared wrappers 重新长成平行基础 UI 系统

---

## 二、弹窗规范

### 目标
弹窗要简单、清晰、结构稳定，不允许出现层级过多、卡片堆叠、窄宽度下布局崩坏。

### 推荐结构
- Header
- Body
- Footer

### 要求
- 弹窗内部优先用标题、说明、内容区、底部操作区组织结构
- 不要在弹窗里堆很多大卡片
- 除代码区 / 预览区外，尽量不使用重边框大容器
- 高级选项默认折叠
- 危险操作必须确认
- 小宽度下优先改单栏，不要强保双栏
- 复制按钮不能遮挡内容
- 代码区应有独立工具栏和内容区
- Footer 操作属于整个弹窗，不属于某个局部区域
- 小屏可使用 fullscreen dialog 或 sheet，不要硬撑桌面 modal

### 禁止项
- 卡片套卡片
- 大面积无意义空白
- 按钮压住代码
- 中文标签被挤成竖排
- 小屏继续双栏硬挤
- 弹窗内容靠大色块提示条强行分层

---

## 三、表单规范

### 目标
表单要有统一节奏和结构，不要像后台拼装页。

### 统一骨架
- FormShell
- FormSection
- FormField
- FormActions
- FormHelpText
- FormErrorText

### 要求
- 标签、说明、输入区、错误提示顺序一致
- 高级设置默认折叠
- 桌面端最多两列
- 窄屏自动单列
- 提交区固定在底部
- 危险字段要有明确提示
- 字段标签用清晰且稳定的字号和字重
- 帮助文案轻量，不抢主内容

### 禁止项
- 每个字段都包成独立小卡片
- 标签风格一页一个样
- 错误提示位置不固定
- 按钮区到处乱放
- 整块粗体堆叠造成“后台表单感”

---

## 四、列表与工具栏规范

### 目标
列表页应像“工具栏 + 列表”，而不是“大筛选表单 + 列表”。

### 统一骨架
- DataTableShell
- AsyncState

### 要求
- 工具栏左侧：搜索 / 常用筛选
- 工具栏右侧：主操作 / 批量操作
- 高级筛选默认折叠
- 搜索框优先支持回车，不强依赖单独搜索按钮
- 搜索占位文案要明确“搜什么”
- 排序属于列表操作，应靠近表格，不应混在筛选主区
- 空态 / 错态 / 载入态统一处理
- 主体视觉重心应回到列表本身

### 禁止项
- 工具栏过重，比列表还抢眼
- 默认露出过多低频筛选项
- 搜索、筛选、排序、批量区顺序页面间不一致
- 为每个页面重新手写一套 table toolbar

---

## 五、交互规范

### 目标
交互要可预测、低学习成本、低误操作，不要让用户猜。

### 通用规则
- 主操作始终稳定放置，不随页面局部变化漂移
- 次操作弱化，危险操作远离主操作
- 同类页面的搜索、筛选、批量操作顺序一致
- 常用操作直出，低频操作收进“更多”
- 高级选项默认折叠
- 空状态、错误状态、加载状态必须有明确反馈
- 不要依赖 hover 才知道关键含义
- destructive 操作都要二次确认或明确防误触机制

### 搜索 / 筛选
- 默认只展示高频筛选
- 更多筛选收进 Popover / Drawer / Dropdown
- 搜索占位文案必须说明搜索目标
- 排序与筛选分离，排序靠近表格

### 批量操作
- 必须明确“作用于选中项”还是“作用于当前分组 / 当前列表”
- 未选择数据时，批量操作禁用
- 显示“已选 N 项”
- 危险批量操作必须确认，并说明影响范围

### 弹窗交互
- 打开弹窗后焦点应进入弹窗
- 关闭弹窗后焦点应回到触发源
- Esc 可关闭普通弹窗，危险确认按业务决定
- 小屏优先保证可读与可操作
- 复制、查看详情、切换平台这类高频动作必须一眼可见

### 提交 / 保存
- 提交中按钮禁用，并显示 loading
- 成功后给明确反馈
- 失败后不能只 toast，要尽量落到表单项或页面态
- 不要让用户不知道是否保存成功

### 微交互
- 复制成功要有即时反馈
- 展开 / 折叠要有明确状态
- tabs / segmented control 切换时不要造成布局剧烈跳动
- loading skeleton 结构尽量接近真实内容

---

## 六、颜色规范

### 目标
颜色服务于语义，而不是装饰。

### 基本原则
- 所有状态颜色必须来源于统一语义映射，而不是页面临时决定
- 颜色优先表达状态风险，其次才是视觉区分

### 统一语义
- default：默认、中性信息
- info：信息、提示、辅助说明
- success：成功、正常、已启用、已通过
- warning：需关注、接近阈值、部分异常、待处理
- danger：失败、错误、高风险、不可逆操作
- disabled：不可用、禁用、不可操作

### 状态映射
- 在线 / 正常 / 已启用 / 成功：success
- 初始化中 / 排队中 / 同步中 / 处理中：info 或 warning，按风险决定
- 部分异常 / 即将超限 / 需要人工关注：warning
- 离线 / 失败 / 删除 / 高危 / 不可逆：danger
- 未配置 / 未启用 / 无数据 / 暂不可用：default 或 disabled

### 使用范围
- Badge
- Alert
- Button
- Progress
- Table row status
- Empty / Error state
- Switch / Toggle 辅助说明
- 图标状态色

### 使用规则
- 同一语义在全项目必须使用同一套颜色映射
- 不允许页面自己定义“在线是蓝色，另一个页面又是绿色”
- danger 只能用于真正风险项，不要滥用
- warning 与 danger 必须明显区分
- disabled 不要看起来像 warning
- 提示条默认轻量，不使用大面积高饱和色块

### 资源指标颜色规则
- 正常：default / success
- 接近阈值：warning
- 超阈值：danger

### 禁止项
- 按“指标类型”固定颜色而不是按风险上色
- 大量直写 slate-* / gray-* / blue-* / red-* 打散 token
- 同页出现过多状态色，破坏扫表效率

---

## 七、字体与排版规范

### 目标
让页面更稳、更清楚、更易扫读。

### 要求
- 标题层级固定
- 正文、说明、辅助文案有明确字号级差
- 代码和 IP 使用等宽字体
- 数字优先使用 tabular nums
- 表格数值列右对齐或结构一致
- 中文标签保持横排阅读，不允许随意 break-all
- 行高、字重、段间距要有统一规则

### 禁止项
- 同级标题字号不一致
- 代码文本像普通浅灰说明文字
- 窄宽度下中文逐字换行
- 数值列忽左忽右、难以扫读

---

## 八、数字、代码与长文本规范

### 数字
- 数值列尽量右对齐或结构统一
- 使用 tabular nums
- 同列单位表达保持一致
- 减少无意义小数位
- 高频指标优先展示最有决策意义的值

### 代码
- 命令、脚本、Token、UUID、IP 使用等宽字体
- 代码区必须有清晰对比度
- 代码可横向滚动，但不要默认被遮挡
- 复制按钮不能覆盖代码内容
- 代码区应有工具栏和内容区，不是大空白框里塞一行字

### 长文本
- 中文默认不要 break-all
- 长 token / URL / UUID / 域名可使用 `overflow-wrap: anywhere`
- 信息展示优先可读，再考虑是否严格不换行
- tooltip 只能补充，不能替代主显示

---

## 九、布局与间距规范

### 目标
通过间距和排版建立层级，而不是靠大量盒子。

### 要求
- 优先通过 spacing、separator、typography、alignment 建层级
- 减少多余边框、阴影、浅灰底块
- 顶部工具栏保持简洁
- 高频信息优先展示
- 低频筛选 / 高级配置折叠
- 列表页看起来应是“工具栏 + 列表”，不是“大表单 + 列表”
- 一屏里不要同时存在多个视觉主角

### 禁止项
- 模块全都长得像卡片
- 页面到处有盒子感
- 重要信息不突出
- 筛选区比列表本身还抢眼
- 用重复浅灰背景和边框制造假层级

---

## 十、信息密度与层级规范

### 目标
后台页面要高效，不要空，也不要挤。

### 规则
- 高频信息优先展示
- 低频信息折叠或降级
- 同一屏不要同时有多个视觉主角
- 工具栏应轻，主内容应重
- 用 spacing、typography、divider 建层级
- 少用大面积描边、浅灰底块、重复卡片
- 不要为了“显得丰富”增加很多块状容器

### 判断标准
看到页面后，用户应能在 3 秒内分清：
- 主要任务是什么
- 主按钮在哪里
- 现在页面状态如何
- 关键信息在哪里

---

## 十一、响应式规范

### 目标
不能只是“缩小”，而要“重排”。

### 要求
- 宽屏可双栏
- 中窄屏改单栏
- 工具栏在小宽度下允许换行，但顺序不能乱
- 弹窗在窄屏可转成单栏或 fullscreen / sheet
- 表单项在窄屏下单列
- 表格允许横向滚动，但核心信息优先保留
- 不允许因为宽度变窄让中文标题竖排化
- 命令区、主操作区、小屏主任务内容应优先拿宽度

### 禁止项
- 小屏继续维持桌面双栏
- 关键内容在窄宽度下被压成不可读
- 中文标签逐字换行
- 复制按钮、图标按钮、操作区挤占正文内容

---

## 十二、可访问性规范

### 要求
- icon-only 按钮必须有 aria-label
- dialog / alert / form label 语义完整
- 焦点态清晰
- tooltip 不能成为理解关键操作的唯一方式
- loading / error / empty 要有明确状态表达
- retry 行为可达、可点击、可读
- 表单 label 与输入控件正确关联
- dialog 打开 / 关闭后焦点管理正确

### 最低要求
- 可感知
- 可操作
- 可理解
- 可恢复

---

## 十三、组件边界规范

### 目标
shared wrappers 保持薄，不重新长成基础 UI 系统。

### 允许
- 业务骨架
- 页面壳
- 领域信息块
- 高频组合模式

### 不允许
- 再包装出一套平行 Button / Dialog / Badge / Input 系统
- 在 domain shared 中重复定义完整基础控件能力
- 为单页方便而新增长期维护成本高的 wrapper

### 原则
- primitives 来自 shadcn/ui
- shared wrappers 只负责组合和约束
- domain helpers 只负责领域展示，不负责重造基础层

---

## 十四、执行顺序

每次做 UI 改动，按这个顺序审查：

1. 布局是否正确
2. 响应式是否安全
3. 主任务是否清晰
4. 交互是否可预测
5. shared wrappers 是否已正确复用
6. shadcn/ui 是否被优先使用
7. 状态颜色是否符合统一语义
8. 排版和可读性是否达标
9. a11y 是否补齐
10. 是否存在平行基础层回流风险

---

## 十五、UI 改动 DoD（Definition of Done）

任何 UI 改动完成前，必须检查：

### 结构
- 布局正确
- 响应式不崩
- 小屏可读
- 不存在中文逐字竖排

### 交互
- 主操作明确
- 危险操作有确认
- loading / empty / error 完整
- 复制 / 展开 / 切换有反馈

### 一致性
- 优先复用 shared wrappers
- 优先复用 shadcn/ui
- 没有新增平行基础层
- 颜色语义一致

### 可读性
- 代码 / 命令可读
- 数字易扫读
- 标签层级清晰
- 不存在无意义大面积空白

### a11y
- icon-only 按钮有 aria-label
- dialog / label / alert 语义完整
- focus 可见
- tooltip 不是唯一信息来源

### 验证
- lint 通过
- typecheck 通过
- build 通过
- test 通过（如有相关测试）

---

## 十六、适用原则

- 优先复用 shadcn/ui + shared wrappers
- 不新增平行基础 UI 层
- 不允许用临时卡片堆叠解决层级问题
- 不允许在窄宽度下让中文标题逐字换行或竖排
- 颜色优先表达状态风险，其次才是视觉区分
- 所有状态颜色必须来源于统一语义映射，而不是页面临时决定
